<h2>二、按并发计费：适合什么样的负载</h2>
<p>并发计费的本质是买"同时在线的通道数"，不看你传输了多少数据。它适合请求密集但响应体小的场景，比如状态查询、批量校验、短对话调用。</p>
<h3>并发数怎么估，别按人头算</h3>
<p>按峰值同时请求数估，不按人数估。十个人如果错峰使用，峰值可能只有三路；三个人同时跑脚本，峰值就是三路以上。取一周内的峰值，乘以一点二作为规划值，比拍脑袋定十路稳妥。</p>
<h3>并发买到但用不满，钱就浪费了</h3>
<p>并发是硬上限，买多了不会退。很多团队按最忙的那一天买，其余时间闲置七八成。做法是先用小规格跑两周，看监控里的并发曲线，再决定是否升档。多数供应商支持按月调整，不必一次买一年。</p>

<h2>三、按流量计费：什么时候会失控</h2>
<p>流量计费的坑不在单价，在放大效应。一次重试等于两次流量，一次超时重发等于两次流量，流式请求中途断开再重来，前面的部分照样计费。单价看着低，账单却可能翻几倍。</p>
<h3>三个常见的流量放大器</h3>
<p>第一是重试，尤其是没有错误分类的盲目重试；第二是未压缩的响应体，长文本场景下压缩前后能差数倍；第三是轮询，客户端为了拿状态每秒问一次，一天下来比正常请求多出几十倍。三项里任何一项没管住，流量计费就会失真。</p>
<h3>先算清一次请求值多少流量</h3>
<p>取一段典型对话，记录请求体与响应体的字节数，加上请求头开销，乘以日均请求数，就是日流量基线。用这个基线去比对报价里的流量包，比看"每月 100G"这种数字直观得多。多数文字类业务的实际用量远小于直觉估计，真正吃流量的是附件和长文档。</p>

<h2>四、混合口径与保底条款怎么读</h2>
<p>市面上更多是混合口径：基础月费含一定并发和流量，超出部分另计。这种结构要重点看三个地方。</p>
<h3>保底、封顶与超量单价</h3>
<p>保底是最低消费，用不满也照收；封顶是费用上限，超过后限速或断服，不是免费。两者要分清，签之前问一句"超量之后是加钱还是限速"。超量单价则要看阶梯，第一档和第二档往往差一倍以上。</p>
<h3>计费周期与结算方式</h3>
<p>按自然月还是按购买日起算，跨月怎么切，退款按什么口径折算，这三点写在合同里比口头说明可靠。预付费套餐要确认剩余额度是否可结转，很多是不可结转的，月底清零。</p>

<h2>常见问答</h2>
<h3>流量计费和并发计费，哪个更便宜？</h3>
<p>答：取决于负载形态。请求多而响应小，按并发通常更省；请求少而单次数据大，按流量更合适。最省的做法是先用小套餐测一周，拿到真实的请求数和流量数，再套两种口径分别算一遍。</p>
<h3>预付费套餐用不完能退吗？</h3>
<p>答：多数不可退，也未必能结转。购买前要问清剩余额度的处理方式、是否支持按月降档、以及中途停用的折算规则。这三点比单价更影响实际支出。</p>
<h3>为什么账单比估算高出一截？</h3>
<p>答：先查三处：失败重试的比例、是否有未压缩的长响应、以及是否有轮询型请求。这三项通常在账单里占比不小，却不在日常监控的视野内。加一条按小时统计的流量曲线，异常很快能看出来。</p>
<h3>多条出口是不是一定更贵？</h3>
<p>答：单条均价可能更贵，但总成本不一定高。把出口按用途拆开之后，每条可以选更贴合的规格，避免为一条线买过大的并发。前提是拆得合理，拆成五六条各买最小规格反而更贵。</p>
